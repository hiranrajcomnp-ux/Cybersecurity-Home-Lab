04 / EVENT VIEWER

Windows Event Viewer

Windows Event Viewer is a built-in Windows utility used to view and analyze event logs. It provides information about system activities including application events, security events, hardware activity, authentication and services.

Event Viewer

Review an Event Log

  1. Open Event Viewer with eventvwr.msc.
  2. Expand Windows Logs and select the relevant log, such as Security or System.
  3. Select Filter Current Log to narrow by event ID, level, account, and time range.
  4. Open a matching event and review both the General and Details views. Record the provider, event ID, computer, timestamp and time zone, account, and message.
  5. Export the original log as EVTX when it is evidence. Preserve the original and perform analysis on a working copy.

06 / SYSMON

Microsoft Sysmon

Microsoft Sysmon is a system monitoring utility that provides detailed information about activity occurring on a Windows system.

Setup and Verify

  1. Obtain Sysmon from Microsoft Sysinternals and verify the download before use.
  2. Open an elevated PowerShell session in the extracted folder and review available options with .\Sysmon64.exe -?.
  3. Install in the authorized lab with .\Sysmon64.exe -accepteula -i. Review and apply an approved configuration appropriate to the monitoring goal before relying on event coverage.
  4. Confirm the service is running with Get-Service Sysmon*.
  5. Open Event Viewer at Applications and Services Logs > Microsoft > Windows > Sysmon > Operational, or query it with Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -MaxEvents 20.
  6. Launch an approved benign test process, such as Notepad, and check for Sysmon Event ID 1. Review the process, parent, user, and command-line fields.
  7. Record the configuration and time range; Sysmon coverage depends on configuration, and verbose rules can increase log volume.

09 / AUDIT POLICY

Windows Audit Policy

Security Policy 
secpol.msc

Account Logon

Click for steps and details

Steps

  1. Open secpol.msc and go to Security Settings > Advanced Audit Policy Configuration > System Audit Policies > Account Logon.
  2. Review Credential Validation and select Success and Failure to match the lab objective.
  3. On domain controllers, review Kerberos Authentication Service and Kerberos Service Ticket Operations as appropriate.
  4. Apply policy through the authorized local or domain policy source, then verify with auditpol /get /category:"Account Logon".

What it records

Authentication credential checks, including NTLM validation (for example, event 4776) and domain Kerberos activity (for example, events 4768, 4769, and 4771). Domain-controller events are generated on the validating server, not necessarily the workstation being accessed.

Account Management

Click for steps and details

Steps

  1. Open the Account Management policy category in Advanced Audit Policy Configuration.
  2. Review User Account Management and Security Group Management; enable Success and Failure according to the investigation need.
  3. Verify effective settings with auditpol /get /category:"Account Management".
  4. In an authorized test environment, make one approved account or group change and confirm the resulting event in the Security log.

What it records

Account and group creation, changes, enablement, disablement, deletion, and membership changes. Common examples include events 4720 (user created), 4722 (user enabled), 4725 (user disabled), and 4732 (member added to a local security group).

Logon / Logoff

Click for steps and details

Steps

  1. Open the Logon/Logoff policy category in Advanced Audit Policy Configuration.
  2. Review Logon and Logoff; consider Special Logon and Other Logon/Logoff Events when required.
  3. Set Success and Failure for the subcategories needed, then check with auditpol /get /category:"Logon/Logoff".
  4. Generate an approved interactive or remote sign-in test and verify the record in the Security log.

What it records

Successful and failed logons (4624 and 4625), logoff activity (4634 and 4647), and special-privilege logons (4672). Use the logon ID to correlate related events on the same host.

Object Access

Click for steps and details

Steps

  1. Open the Object Access policy category and select only relevant subcategories, such as File System, Registry, or Removable Storage.
  2. For file and registry auditing, configure appropriate SACLs on the specific objects; enabling the audit subcategory alone does not generate object-access events.
  3. Verify the effective audit settings with auditpol /get /category:"Object Access".
  4. Perform an approved access test against a lab object and inspect the Security log.

What it records

Access attempts against audited objects, including events such as 4663 when the applicable policy and object SACL are configured. Scope auditing narrowly because broad object auditing can create substantial log volume.

Policy Change

Click for steps and details

Steps

  1. Open the Policy Change category and review Audit Policy Change, Authentication Policy Change, and relevant firewall or filtering-platform policy subcategories.
  2. Enable Success and Failure where appropriate to record changes and failed attempts.
  3. Verify with auditpol /get /category:"Policy Change".
  4. Make a documented, approved test-policy change in the lab and confirm it is logged, then restore the original setting and verify restoration.

What it records

Changes to audit, authentication, authorization, and some firewall policies. Event 4719 is an example of a system audit policy change. Restrict who can change policy and retain a record of approved changes.

Privilege Use

Click for steps and details

Steps

  1. Open the Privilege Use category and review Sensitive Privilege Use before enabling broader privilege auditing.
  2. Choose Success and Failure based on the investigation objective and expected event volume.
  3. Verify with auditpol /get /category:"Privilege Use".
  4. Perform an approved privileged action in the lab and verify the expected event and account in the Security log.

What it records

Use of sensitive system privileges and related privileged operations, including events such as 4673 and 4674. These records provide context for privileged activity but do not, on their own, prove misuse.

System

Click for steps and details

Steps

  1. Open the System category and review Security State Change, Security System Extension, System Integrity, and other subcategories relevant to the host.
  2. Set Success and Failure as needed, then verify with auditpol /get /category:"System".
  3. Correlate resulting Security events with the System event log and record the host and time zone.

What it records

Changes to system security state, security services, and integrity checks. For example, event 4616 can record a system time change, which may affect timeline analysis.

Detailed Tracking

Click for steps and details

Steps

  1. Open the Detailed Tracking category and review Process Creation and Process Termination for endpoint monitoring.
  2. Enable only the subcategories needed and verify with auditpol /get /category:"Detailed Tracking".
  3. If process command-line capture is required, configure the separate command-line inclusion policy and assess whether arguments could contain secrets.
  4. Run an approved test process and confirm event 4688 appears with the expected process details.

What it records

Process starts and other detailed activity; event 4688 records process creation when configured. Process auditing can produce high event volume, and command-line arguments may contain sensitive information.

These are recommended configuration and verification steps; this report does not state that the audit settings were changed. Check effective policy before making changes because domain Group Policy may override local settings. Enable only the subcategories needed to balance useful telemetry and manageable log volume.

16 / COLLECTION PLAN

Recommended Evidence Collection

01

Windows Security Event Log

Select to view collection details

What to collect

Export the Security channel for the investigation window. Preserve event IDs, provider, account, computer name, and original timestamps so logon, privilege-use, and audit-policy events can be correlated.

Collection notes

  • Save an original EVTX export and analyze a separate working copy.
  • Record the time range, host, export time, and any relevant audit-policy gaps.
  • Protect the file because Security logs can contain sensitive account and activity details.

02

Windows System Event Log

Select to view collection details

What to collect

Export the System channel for the same time range. Include service start and stop, driver, shutdown, startup, and operating-system events that may explain or contextualize activity in other logs.

Collection notes

  • Preserve the original EVTX file and document the host and time zone.
  • Correlate records by timestamp and provider; proximity alone does not prove causation.
  • Note missing or overwritten periods that could limit the timeline.

03

Sysmon Operational Log

Select to view collection details

What to collect

Export Microsoft-Windows-Sysmon/Operational. Review process creation, network connections, file changes, and image-load events when those event types are enabled by the installed configuration.

Collection notes

  • Record the Sysmon service version and configuration used during collection.
  • Keep the raw EVTX alongside any filtered CSV or screenshots.
  • Filtering can omit context, so document event IDs and query criteria.

04

PowerShell Operational Log

Select to view collection details

What to collect

Export Microsoft-Windows-PowerShell/Operational for the relevant period. When logging is enabled, events such as 4103 and 4104 may provide module or script-block activity.

Collection notes

  • Logging coverage depends on policy and configuration; absence of an event is not proof a command did not run.
  • Retain the original EVTX and note the host, time range, and logging policy.
  • Review exports for credentials, tokens, or other secrets before sharing them.

05

Measured Boot diagnostic files

Select to view collection details

What to collect

Save available Measured Boot diagnostics and record the device model, firmware mode, Secure Boot state, and TPM status relevant to interpreting them.

Collection notes

  • Record the exact collection method, date, and system used.
  • Preserve the original diagnostic output; do not infer a boot compromise from a warning alone.
  • Include firmware or platform limitations that affect whether measurements are available.

06

Windows Defender configuration

Select to view collection details

What to collect

Capture Defender status and preferences, including protection state, engine and intelligence versions, exclusions, and relevant policy settings.

Collection notes

  • Use read-only queries such as Get-MpComputerStatus and Get-MpPreference.
  • Record collection time and whether policy is managed locally or centrally.
  • Review exclusions carefully; their presence alone does not establish malicious activity.

07

Windows Firewall configuration

Select to view collection details

What to collect

Record firewall profile state, default inbound and outbound actions, active profile, and rules relevant to the system under review.

Collection notes

  • Read-only commands such as Get-NetFirewallProfile and Get-NetFirewallRule can capture configuration.
  • Include rule direction, action, protocol, ports, program, and enabled state when applicable.
  • Save the output with host and timestamp; avoid changing policy during evidence collection.

08

Local user list

Select to view collection details

What to collect

Capture local account names, enabled state, and other relevant account properties at the time of review.

Collection notes

  • A read-only query such as Get-LocalUser provides a point-in-time view.
  • Record the host, time, and method; the list does not include every identity source in a domain environment.
  • Compare against an approved baseline before labeling an account unexpected.

09

Local administrator membership

Select to view collection details

What to collect

Record the members of the local Administrators group, including whether each entry is a local account, domain account, or nested group where the system can resolve it.

Collection notes

  • Use a read-only query such as Get-LocalGroupMember -Group Administrators.
  • Capture the host and timestamp and retain the command output.
  • Membership indicates privilege, not intent; assess it against the authorized baseline.

10

Listening network ports

Select to view collection details

What to collect

Capture listening TCP endpoints and relevant UDP endpoints together with local address, port, process ID, and process name.

Collection notes

  • Use read-only commands such as Get-NetTCPConnection -State Listen and Get-NetUDPEndpoint.
  • Record collection time because network state changes frequently.
  • A listening port is not by itself evidence of compromise; verify the owning process and expected service.

11

Relevant screenshots

Select to view collection details

What to collect

Capture relevant interface state, event details, configuration, or command output with enough context to identify the system and observation.

Collection notes

  • Keep the original image file and record its filename, capture time, host, and related evidence ID.
  • A screenshot supplements original logs and files; it does not replace them.
  • Check for visible usernames, email addresses, tokens, or other sensitive data before publication.

12

Command output

Select to view collection details

What to collect

Save the exact command, unaltered output, execution context, collection time, and exit status for each relevant query.

Collection notes

  • Prefer a text transcript or exported file over retyped results.
  • Note shell version, host, and whether elevated privileges were used.
  • Redact secrets only in a documented sharing copy and retain the protected original.

13

SHA-256 hashes

Select to view collection details

What to collect

Generate a SHA-256 digest for every collected file and maintain a manifest linking each digest to the evidence ID and filename.

Collection notes

  • For example, use Get-FileHash -Algorithm SHA256 on the original after acquisition.
  • Recalculate after transfer to check that the copy has not changed.
  • A matching hash supports integrity since hashing; it does not prove the source or interpretation is authentic.

14

Investigation timeline

Select to view collection details

What to collect

Build a chronological record with timestamp, time zone, host, source, event or evidence ID, and a concise description of each observation.

Collection notes

  • Retain original timestamps and document any time normalization.
  • Link each entry to its source file so another reviewer can reproduce the finding.
  • Separate observed facts from hypotheses; temporal order alone does not establish causality.

18 / CONCLUSION

Conclusion

The Windows cybersecurity laboratory demonstrates how a security analyst can combine system configuration, Windows event logging, Sysmon, PowerShell logging, security controls and evidence handling into a structured defensive workflow.

Windows Event Viewer provides the basic event-monitoring capability, while Sysmon can provide additional system telemetry. PowerShell logging provides further visibility into administrative and scripting activity.

Windows hardening complements monitoring by reducing unnecessary exposure and strengthening security controls.

The TPM-WMI Event 1040 and DistributedCOM Event 10016 observed on the laboratory computer demonstrate why individual Windows events should be investigated in context. An event should be documented, correlated with related evidence, and investigated before drawing conclusions about its significance.
